# 선박 매칭 모델 상세 설명

> 이 문서는 기존 23개 특징 베이스라인의 설명을 보존한 것입니다. 37개 특징 추가 실험은 [선박명 개선 결과](NAME_IMPROVEMENT_RESULTS.md), 최신 n-gram 및 모든 검색 조합 실험은 [검색 조합 결과](RETRIEVAL_COMBINATIONS.md), 최종 제출 ZIP은 E009 기록을 확인하세요.

## 1. 모델 개요

생성한 모델은 **호출부호 조회와 LightGBM 후보 비교를 결합한 선박 매칭 시스템**이다. 입출항 기록 한 행을 받아 공식 카탈로그에서 같은 선박의 ID 하나를 반환한다.

| 항목 | 내용 |
|---|---|
| 최종 예측값 | target_vessel_id |
| 공식 학습 기록 | 12,222행 |
| 공식 카탈로그 | 78,595척 |
| 핵심 학습 모델 | LightGBM 이진 분류기 |
| 비교 특징 수 | 23개 |
| 결정트리 수 | 350개 |
| 학습 데이터 출처 | 공식 train.csv와 vessel_catalog.csv |
| 최종 제출물 | submit.zip |

LightGBM은 선박 ID를 직접 다중 클래스 분류하지 않는다. 대신 **입력 기록과 후보 선박이 같은 선박인지** 평가한다. 각 후보의 점수를 계산하고 가장 높은 후보의 ID를 선택하므로, 학습에서 정답으로 보지 못한 ID도 카탈로그에 있으면 선택할 수 있다.

가중치 파일 이름은 ranker.txt이지만, 실제 목적함수는 binary이다. 전용 순위 학습 알고리즘인 LambdaRank를 사용한 것은 아니다. 분석 예제로 만든 LogisticRegression은 이 제출 모델에 포함되지 않는다.

실제 제출 ZIP의 script.py, matcher.py, ranker.txt, assets.json이 설명에 사용한 작업 파일과 동일함을 확인했다.

## 2. 시스템 구성과 입력 정보

| 구성 요소 | 역할 |
|---|---|
| 고정 학습 사전 | 호출부호·별칭과 ID의 관계, 선종·국적 대응 비율 저장 |
| 카탈로그 검색 인덱스 | 이름 표현, 발음 키, 톤수 정렬, 선종별 후보 목록 준비 |
| 후보 검색기 | 해당 입력 한 행으로 여러 검색 경로의 후보를 모음 |

사용하는 입력은 sample_id, vessel_name, call_sign, gross_tonnage, international_gross_tonnage, flag_name, vessel_type이다. sample_id는 출력 행을 식별하는 용도이며 예측 특징으로 사용하지 않는다. arrival_year도 현재 모델의 예측 특징으로 사용하지 않는다.

카탈로그에서는 vessel_id, vessel_name, gross_tonnage, vessel_type, flag_name을 사용한다. size, unit, deadweight_tonnage는 현재 비교 특징에 포함하지 않는다.

## 3. 예측 동작 과정

```text
입출항 기록 한 행
    ↓
학습 호출부호 사전에 존재하는가?
    ├─ 예: 연결된 ID가 현재 카탈로그에 있으면 바로 반환
    └─ 아니요: 이름·발음·톤수로 후보 검색
                    ↓
              중복 후보 제거
                    ↓
        입력과 각 후보의 비교 특징 23개 계산
                    ↓
          LightGBM으로 후보별 점수 계산
                    ↓
             최고점 선박 ID 반환
```

### 3.1 호출부호 조회

공식 학습 데이터에서 call_sign → target_vessel_id 사전을 만든다. 하나의 ID로 명확하게 대응하는 호출부호만 저장한다. 최종 사전에는 5,851개 호출부호가 있다.

입력 호출부호가 사전에 있고 연결된 ID가 현재 카탈로그에도 존재하면 곧바로 반환한다. 이 경로에서는 이름·톤수의 충돌 여부를 추가 확인하지 않으며 LightGBM을 실행하지 않는다.

검증용 사전은 검증 기록을 제외한 학습 데이터에서만 생성했다. 추론 중 다른 테스트 기록에서 호출부호나 별칭을 새로 학습·누적하지 않는다.

### 3.2 이름 전처리

이름을 다음 세 가지 표현으로 변환한다.

1. **정규화 문자열:** Unicode NFKC 정규화, 대문자 변환, 문자·숫자만 보존한다.
2. **로마자 문자열:** Unidecode로 로마자화한 뒤 같은 정규화를 적용한다.
3. **발음 키:** 로마자 문자열에서 일부 자음을 통합하고 모음 등을 제거해 단순화한다.

예를 들어 모닝쿠리어는 로마자화 후 MONINGKURIEO 형태가 된다. 이를 MORNINGCOURIER와 비교하면 한글과 영어 원문을 직접 비교하는 것보다 공통점을 찾기 쉽다.

발음 키는 PH→F, SH→S, NG→N 등의 치환과 일부 자음 통합, 모음 등의 제거, 연속 중복 문자 축약을 사용한다. 이는 언어 의미를 이해하는 번역 모델이나 학습된 음역 모델이 아니라 규칙 기반 근사 처리이다.

### 3.3 후보 검색

| 검색 경로 | 한글 이름 | 비한글 이름 |
|---|---|---|
| 이름 | 로마자 유사도 상위 60개 + 발음 키 유사도 상위 60개 | 정규화 문자열 유사도 상위 24개 |
| 톤수 | 각 입력 톤수에 가까운 후보 60개씩 | 각 입력 톤수에 가까운 후보 24개씩 |
| 선종별 보완 | 학습 대응 비율이 높은 선종 최대 2개에서 각 톤수에 가까운 후보 40개씩 | 별도 적용하지 않음 |
| 학습 별칭 | 정규화 이름이 학습 별칭과 일치하는 ID 추가 | 동일 |

검색 결과를 합친 뒤 ID 중복을 제거하므로 최종 후보 수는 기록마다 다르다. 두 톤수가 같거나 검색 경로가 겹치면 실제 후보 수는 각 검색 개수의 단순합보다 작다.

톤수가 비어 있으면 해당 검색 경로는 생략한다. 학습 별칭은 후보를 추가하는 데 사용하며 바로 정답을 확정하는 규칙은 아니다. 최종 별칭 사전의 정규화 이름 키는 5,857개이다.

| 구분 | 특징 | 의미 |
|---|---|---|
| 이름 | exact | 비어 있지 않은 정규화 이름의 정확 일치 |
| 이름 | ratio | 전체 정규화 문자열 유사도 |

| 숫자 | digits_equal | 이름 속 숫자열 일치 여부 |
| 숫자 | digits_missing | 입력 이름에 숫자가 없는지 |
| 톤수 | gross_gap | 입력 총톤수와 후보 총톤수의 상대 오차 |
| 톤수 | international_gap | 입력 국제총톤수와 후보 총톤수의 상대 오차 |
| 톤수 | best_gap | 두 상대 오차의 최솟값 |
| 톤수 | gross_exact | 총톤수 상대 오차가 1e-6보다 작은지 |
| 톤수 | international_exact | 국제총톤수 상대 오차가 1e-6보다 작은지 |
| 결측 | gross_missing | 입력 총톤수가 비어 있는지 |
| 결측 | international_missing | 입력 국제총톤수가 비어 있는지 |
| 결측 | catalog_gross_missing | 후보 총톤수가 비어 있는지 |
| 범주 | type_probability | 입력 선종에 대한 후보 선종의 학습 대응 비율 |
| 범주 | flag_probability | 입력 국적에 대한 후보 국적의 학습 대응 비율 |
| 결측 | flag_missing | 입력 국적이 비어 있는지 |
| 언어 | is_hangul | 입력 이름에 한글 음절이 포함됐는지 |
| 길이 | name_length | 입력 정규화 이름 길이 |
| 길이 | catalog_name_length | 후보 정규화 이름 길이 |

문자열 유사도는 RapidFuzz로 계산하고 0–1 범위로 변환한다. 톤수 상대 오차는 다음과 같다.

```text
relative_gap(q, c) = abs(q - c) / max(q, c, 1)
```

톤수가 없거나 유효하지 않으면 원래 톤수를 평균으로 채우지 않는다. 상대 오차 특징에 2.0이라는 고정 센티널을 넣고 결측 표시를 따로 제공한다. 정상 양수 톤수끼리의 상대 오차 범위 밖에 값을 두어 정보 없음과 작은 오차를 구분한다.

선종·국적 대응 비율은 공식 학습 정답을 카탈로그에 연결해서 만든다. 예를 들어 특정 입력 선종에 연결된 카탈로그 선종의 빈도를 비율로 표현한다. 동일 선박과 동일 입력 범주의 반복 기록은 중복 제거해 횟수를 부풀리지 않는다. 외부 선박 DB나 외부 정답 매핑표를 사용하지 않는다.

### 3.5 최종 선택과 출력

각 후보의 비교 특징을 LightGBM에 넣고 점수가 가장 높은 후보를 선택한다.

```text
prediction(q) = 후보 c 중 LightGBM(x(q, c))가 가장 큰 후보의 ID
```

후보는 ID 기준으로 고정 정렬하며 동점이면 앞선 후보를 선택한다. 입력 순서를 바꾸어도 동일한 기록의 결과가 유지되도록 설계했다.

script.py는 data/test.csv와 data/vessel_catalog.csv를 읽고 output/submission.csv에 sample_id, target_vessel_id 두 컬럼을 저장한다. 테스트 원본 기록이나 개별 예측을 로그로 출력하지 않는다.

## 4. 학습 방법과 설정

### 4.1 학습 쌍 구성

전체 공식 학습 기록은 12,222행이다. 이름·두 톤수·국적·선종·정답이 같은 중복을 줄여 6,683개 비교 입력 기록을 사용했다. 최종적으로 입력–후보 쌍 330,132개를 생성했다.

| 후보 관계 | 학습 라벨 |
|---|---:|
| 정답 선박 | 1 |
| 다른 선박 | 0 |

오답은 실제 검색 결과에서 가져오므로 이름이나 톤수가 비슷한 어려운 오답을 포함한다. 후보가 100개보다 많으면 이름·발음 유사도와 톤수 오차로 계산한 기준의 상위 80개, 톤수 오차가 작은 상위 20개, 정답을 합쳐 학습량을 제한한다. 중복을 제거하므로 이 수들의 단순합과 실제 개수는 다르다.

학습에서는 검색 목록에 정답이 없을 경우 양성 예제를 만들기 위해 정답을 추가한다. 검증과 실제 추론에서는 정답을 강제로 추가하지 않는다. 학습 쌍의 검색에서는 별칭 추가도 끄고, 자기 정답을 별칭으로 조회하는 데 의존하지 않도록 했다.

### 4.2 목적함수와 언어 가중치

LightGBM은 후보 쌍의 동일 선박 여부를 이진 분류한다. 한글 기록의 높은 평가 비중을 반영하기 위해 학습용 중복 제거 기록의 언어 비율에 따라 다음 가중치를 준다.

```text
한글 기록에서 생성한 쌍의 가중치 = 0.7 / 학습 한글 기록 비율
비한글 기록에서 생성한 쌍의 가중치 = 0.3 / 학습 비한글 기록 비율
```

가중치는 각 후보 쌍에 적용한다. 기록마다 후보 수가 다르므로 모든 입력 행의 총 학습 가중치가 같지는 않다. 또한 이진 분류 손실을 줄이는 것과 최종 후보 Top-1 정확도를 높이는 것은 완전히 같은 목적이 아니다.

### 4.3 주요 하이퍼파라미터

| 설정 | 값 | 의미 |
|---|---:|---|
| n_estimators | 350 | 결정트리 수 |
| learning_rate | 0.05 | 각 새 트리의 반영 정도 |
| num_leaves | 31 | 트리당 최대 잎 수 |
| max_depth | -1 | 별도 깊이 상한 없음; 잎 수 등으로 복잡도 제한 |
| min_child_samples | 40 | 잎당 최소 표본 수 관련 설정 |
| colsample_bytree | 0.9 | 트리별 특징 사용 비율 |
| reg_lambda | 2 | L2 규제 |
| random_state | 20261016 | 재현을 위한 시드 |
| n_jobs | 4 | 학습 스레드 수 |
| deterministic | True | 결정적 실행 설정 |

트리는 앞선 예측의 손실을 줄이는 방향으로 순차적으로 추가된다. 표준화가 필요한 선형 모델과 달리 현재 LightGBM 특징에는 별도의 StandardScaler를 적용하지 않았다.

조기 종료나 광범위한 하이퍼파라미터 탐색은 수행하지 않았다. 추론 시 후보 점수 계산은 num_threads=1로 실행한다.

## 5. 검증 설계와 실측 결과

검증에서는 정답 선박 ID의 약 20%를 그룹으로 보류했다. 남은 기록 중 20%를 한글 여부로 층화해 별도 행 보류 세트로 만들었다. 두 보류 세트를 모두 제외한 7,857행으로 검증 모델과 사전을 학습했다.

| 검증 조건 | 기록 수 | 한글 정확도 | 비한글 정확도 | 공식 산식 가중 점수 |
|---|---:|---:|---:|---:|
| 학습에 없는 선박 | 2,400 | 92.68% | 99.95% | 94.86% |
| 기존·새 선박 혼합 | 1,965 | 97.97% | 99.83% | 98.53% |

공식 산식은 0.7 × 한글 정확도 + 0.3 × 비한글 정확도이다. 혼합 세트의 70.89%는 학습에서 본 선박이므로 호출부호 조회의 도움을 받는다. 98.53%를 처음 보는 선박의 성능으로 해석해서는 안 된다.

새 선박 보류에는 1,171척이 포함되며 한글 표본은 205행·71척이다. 정답 후보 포함률은 한글 99.51%, 비한글 99.95%였다. 후보 수가 고정된 검증은 아니므로 이를 특정 K의 Recall@K로 부르지 않는다.

한글의 정답 후보 포함률과 최종 정확도 차이는 정답을 후보로 찾은 후 잘못 고르는 오류가 남아 있음을 보여준다. 새 선박 보류의 오분류는 16행·7척이었다.

검증이 끝난 뒤 제출 모델은 전체 공식 학습 데이터로 다시 학습했다. 위 점수는 검증 모델의 로컬 결과이며, 전체 데이터로 학습한 제출 모델의 비공개 평가 점수가 아니다. 단일 분할 결과이고 5-fold 평균이나 통계적 신뢰구간은 계산하지 않았다.

## 6. 실행 특성과 규정 준수

- 추론에는 고정 학습 사전, 현재 입력 행, 공식 카탈로그만 사용한다.
- 다른 테스트 행의 평균·빈도·그룹 투표·누적 별칭·분포 보정을 사용하지 않는다.
- 같은 행의 전체 입력·부분집합·단독·순서 변경 실행에서 예측 일치 검사를 수행했다.
- 별도 임시 폴더에서 ZIP을 풀고 네트워크 연결을 막은 상태로 진입점을 검사했다.
- 읽기 전용 입력 보존, 출력 컬럼·순서·카탈로그 ID 유효성, 빈 입력 처리를 검사했다.
- 새 선박 2,400행의 로컬 예측은 약 37.5초였다. 이 측정은 인덱스 생성·파일 로딩·저장을 제외하며 서버 전체 실행 시간을 보장하지 않는다.
- ZIP 크기는 657,921바이트이다. 모델 가중치는 LightGBM 네이티브 텍스트, 사전은 JSON으로 저장했다.

로컬 검증 환경은 Python 3.12이며 평가 서버 안내는 Python 3.11이다. 공식 서버에서의 실행과 점수는 아직 확인하지 않았다.

## 7. 한계점

### 7.1 호출부호를 강하게 신뢰함

학습에 있는 호출부호는 다른 필드와의 충돌 검사 없이 바로 ID로 연결한다. 호출부호 오류·재사용·잘못된 학습 매핑이 있으면 잘못 확정할 수 있다. 관측 학습 데이터의 일대일 관계가 모든 상황에서 유지된다는 보장은 없다.

### 7.2 단순한 한영 이름 표현

로마자화와 발음 키는 불규칙 음역, 약칭, 이니셜, 이름 변경을 충분히 처리하지 못할 수 있다. 모음 제거와 자음 통합은 서로 다른 이름을 비슷하게 만드는 부작용도 있다. 다국어 임베딩이나 학습된 음역 모델은 사용하지 않았다.

### 7.3 후보 검색 실패

이름 변형이 심하고 톤수도 없거나 크게 틀리면 정답이 후보 목록에 들어오지 않을 수 있다. 이후 분류기는 검색되지 않은 ID를 선택할 수 없다. 이름 검색은 카탈로그 전체 문자열 목록을 비교하므로 더 큰 데이터에서 비용이 증가할 수 있다.

### 7.4 항상 하나를 선택하는 구조

점수는 확률 형태로 출력되지만 실제 정답 확률로 보정하지 않았다. 점수 0.9를 정답 확률 90%라고 해석할 근거는 없다. 최소 신뢰도 기준이나 판단 보류 기능 없이 최고점 후보를 반환한다.

이름·톤수 등으로 후보를 전혀 찾지 못하면 코드상 ID 정렬의 첫 선박을 반환한다. 극단적인 결측·비정상 입력에서는 의미 있는 판단이 아닐 수 있다.

### 7.5 범주와 표본의 제한

학습 데이터의 한글 기록은 1,191행·382척이다. 처음 보는 입력 선종·국적에는 학습 대응 정보가 없으며, 드문 범주의 비율 추정도 불안정할 수 있다. 작은 선박·희귀 선종·미관측 국적에 대한 일반화는 충분히 검증하지 않았다.

### 7.6 학습 목표와 최종 지표의 차이

쌍별 이진 분류 손실을 최적화하므로 한 기록 안에서 정답이 반드시 1위가 되도록 직접 학습하는 목적함수는 아니다. 후보 수가 다른 기록의 학습 기여도도 달라진다. 점수의 확률 보정, 기록별 후보 수 정규화, 직접적인 순위 학습은 별도 비교 대상이다.

### 7.7 검증 및 비교 실험 부족

현재 결과는 단일 분할이다. 여러 시드·5-fold·연도순 검증, 모델 간 공정한 비교, 특징 제거 실험을 수행하지 않았다. 따라서 각 특징이나 호출부호 경로가 점수를 얼마나 높였는지 정량적으로 분리하지 못했다.

### 7.8 평가 서버 실측 부재

로컬 실행 검사와 서버 실행은 동일하지 않다. 운영체제·패키지 버전·부하·전체 테스트 규모에 따른 시간과 호환성은 실제 평가 실행에서 확인해야 한다.

## 8. 개선 우선순위

| 우선순위 | 작업 | 확인할 효과 |
|---|---|---|
| 1 | 호출부호 조회 결과와 이름·톤수 충돌 검사 | 잘못된 호출부호를 곧바로 확정하는 위험 완화 |
| 2 | 한글 음역·약칭·숫자·접두어 구분 개선 | 비슷한 후보 사이의 최종 선택 오류 감소 |
| 3 | 어려운 오답 구성과 후보 수별 학습 가중치 비교 | 쌍별 학습과 행별 Top-1 목표의 차이 점검 |
| 4 | 같은 후보에서 LogisticRegression·LightGBM·CatBoost 등 비교 | 검색 차이를 배제한 분류기의 효과 확인 |
| 5 | 선박 그룹 교차검증·연도순·희귀 집단 검증 | 성능의 안정성과 적용 범위 확인 |
| 6 | 오프라인 전체 실행·메모리·실제 서버 검사 | 제출 환경의 호환성과 실행 규격 확인 |

위 항목은 개선 계획이며, 성능 향상을 실제로 확인한 결과는 아니다.

## 9. 구현 및 실측 근거

| 파일 | 내용 |
|---|---|
| model/matcher.py | 고정 사전 생성, 후보 검색, 특징 생성, 예측 |
