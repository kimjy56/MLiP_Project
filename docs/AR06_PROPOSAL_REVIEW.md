# AR-06 세 가지 개선 제안 검토

검토 ID: `AUDIT-AR06-PROPOSAL-01` · 2026-10-25 KST. 대상은 현재 작업 트리의 `AR-06/run_ar06.py`, `AR-06/script.py`, 두 보관 `model.json`이다. 공개 train·fold 집계와 소스 검토를 수행했다. 매칭기 실행·재학습·성능 비교는 수행하지 않았으며 성능 지표는 미측정이다.

## 판단

제안에는 유효한 연구 방향이 있지만, 세 항목을 리더보드 약 0.90의 **확인된 원인** 또는 **즉시 해결책**으로 단정할 수 없다. 한글 톤수 합집합, 자음 골격과 발음 호환, train 학습 자산은 이미 존재한다. 실제로 새로 비교할 것은 안전 조회 정책, 접두사 밖의 전역 검색, 기존 톤수 점수에 대한 조건부 상호작용이다. 현재 모델이 실제 10/22 업로드 ZIP과 동일하다는 증거도 별도로 필요하다.

| 제안 | 확인한 현재 구현 | 판단 |
|---|---|---|
| 조회 비활성화로 seen 선박 손실 | 조회 기본값 false. 호출부호·이름 일치 시 즉시 ID 반환하는 분기는 존재 | 활용 기회는 있으나 test의 seen 비율·현재 오답 기여는 미확인 |
| 수동 단어 사전 없이는 한글 후보 생성 불가 | 학습 단어·음절, 기본 로마자, 발음, 자음 골격, 톤수 검색이 함께 존재 | 전제가 다름. 접두사 밖 전역 검색은 신규 비교 가치 있음 |
| 톤수 ±6% 후보를 무조건 합집합 | 이미 GT·IGT 각각 약 ±9.8%를 제한 없이 합집합 | 같은 톤수 값이면 ±6% 후보는 기존 범위에 포함되어 후보 추가 효과 없음 |
| model.json에 train 미반영 가능성 | 전체 train으로 fit하는 경로와 실제 조회·음역 자산 존재 | 현재 보관 자산에서는 미반영 근거 없음 |
| 톤수 ±1.5%·국적·선종 가산 | 기존에도 톤수 점수와 국적·선종 보정 존재 | 새로운 조건부 상호작용 가설. 별도 비교 전에는 가산 크기·효과 미확정 |

## 1. Safe Train Lookup

### 확인된 사실

- `script.py:1417`, `2048`: `model.get("use_train_lookup_default", USE_TRAIN_LOOKUP)`로 JSON 설정이 상수보다 우선한다. 두 모델 JSON의 값은 false다. **파이썬 상수만 True로 바꾸면 활성화되지 않는다.**
- `run_ar06.py:2153`, `2161`, `2206`: OOF fit·predict와 최종 fit 모두 false를 명시한다. 최종 자산 정책과 검증 시 정책을 의도적으로 설계해야 한다.
- `script.py:1126`부터 호출부호·이름별 Counter를 만들고 `most_common(1)`로 대표 ID만 저장한다. `1464`, `1478`, `1678`의 직접 반환 분기에는 유일 매핑 확인·톤수 검사·상충 정보 검사가 없다.
- 공개 train 12,222행, 5,851척에서 호출부호 키도 5,851개다. 복수 ID 호출부호는 0개이며 현재 callsign_lookup과 행별 정답 불일치도 0개다. 이는 학습 자료의 일관성 확인이며 보류 예측 성능이 아니다.
- 선박 그룹 fold에서 동일 ID의 복수 fold 배정은 0건이다. 조회가 작동하지 않을 수 있어도 보류 행이 다른 ID의 키에 잘못 일치하는 Break는 검사해야 한다. 행 분할 보조 fold에서는 8,702/12,222행(71.1995%)의 정답 ID가 다른 fold에도 존재한다. 이 비율은 실제 test의 seen 비율이 아니다.

### 수정 설계 — 아직 구현하지 않음

1. 각 학습 fold에서 호출부호별 **전체 ID 집합과 관측 수**, 이름별 **전체 ID 후보 목록**을 새 JSON 스키마에 저장한다. 기존 다수결 자산만으로는 버려진 충돌 여부를 복원할 수 없다. 현재 전체 train 호출부호에는 충돌이 없더라도 안전 조건을 코드로 보장한다.
2. 유일 호출부호, 카탈로그 ID 소속, 결측 표식 제거를 확인한다. 이름·제원과 강하게 충돌하면 직접 확정하지 않고 기존 랭커의 후보로 넘기는 정책을 비교한다. 학습에서 유일하다는 사실은 미래의 재할당·입력 오류를 배제하지 않는다.
3. 이름 조회에는 정규화된 관측 별칭의 모든 ID를 보존하고, 양수·유한한 GT/IGT 중 하나와 카탈로그 GT의 상대 오차가 5% 이하인지 검사한다. 분모는 카탈로그 GT로 명시한다. 이름·톤수 조건을 만족하는 복수 ID, 호출부호와 이름의 불일치, 근접 자매선이 있으면 확정하지 않는다. 별칭 이름과 카탈로그 이름은 개명 때문에 다를 수 있다.
4. 직접 확정과 **후보 추가만 하는 정책**을 분리 비교한다. 이름+톤수 5%는 자매선을 완전히 구별하지 못하므로 100% 정확도를 전제하지 않는다.
5. `use_train_lookup_default`를 포함하는 하나의 명시적 설정으로 호출부호와 이름 조회를 제어한다. G5 퇴보 검사와 행 분할 보조 검증을 구분하고, 후자는 seen/unseen별 Coverage·Precision·Fix/Break를 함께 기록한다.

## 2. 한글 검색 — 이미 있는 것과 새로 추가할 것

`retrieve_hangul`, `first_char_map`, `ngram3_map`, `tonnage_candidates`, `best_sim`이라는 식별자는 이번 두 파일에 없다. 실제 한글 검색은 `predict_rows` 안에 있다. 따라서 해당 이름을 대상으로 한 수정안은 현재 코드에 직접 적용되는 패치가 아니다.

- `script.py:881–911`: 단어 사전이 없어도 학습 음절 후보와 `syllable_to_rom`으로 두 문자열을 만든다.
- `914–988`: 학습 단어 Top-2·수동 단어·음절 변형·기본 로마자 후보를 함께 생성한다. 수동 단어 전체 등록이 필수인 구조가 아니다.
- `628–710`: `en_to_phonetic`, `kr_to_phonetic`, `consonant_skeleton`이 이미 있다. 골격에서 C/K/Q/G, F/P/V/B, L/R, Z/S, D/T 등을 합친다. **J까지 Z/S와 합치는 것은 추가 변화**이며 혼동 후보 증가를 측정해야 한다.
- `1274–1279`, `1314–1326`: 이름·골격·발음의 **앞 3문자** 인덱스다. 문자열 전체에서 추출한 모든 3-gram의 역색인은 아니다. 첫 부분이 달라지면 후보를 놓칠 가능성은 남는다.
- `1741–1782`: exact, GT·IGT 톤수, 이름 접두사, 자음 접두사, 발음 접두사, 단어와 변형, 숫자 후보를 합친다. 톤수창은 `rel_tol=0.098, max_cands=None`이다. 실제 경계는 `ton*(1±0.098)±2`이며 카탈로그 GT 기준 상대 오차 식과 정확히 같은 정의는 아니다.
- `1783–1788`: 여전히 비어 있을 때 30% 톤수창 200개, 그마저 없으면 카탈로그 0번 행을 사용한다. 이 대체 경로 때문에 최종 집합이 비지 않는 것과 정답 포함은 별개다.

우선 비교할 변경은 **기존 후보 + 전역 문자 2~4gram**이고, 다음은 **기존 후보 + 전역 자음/발음 3-gram**이다. 인덱스는 공식 카탈로그에서 고정 구축하고 조회마다 갱신하지 않는다. 단순 공통 gram 하나로 전부 추가하면 짧은 골격·흔한 gram 때문에 후보가 급증할 수 있어 겹침 점수와 후보 예산, vessel_id 동점 처리가 필요하다.

`model/ngram_retrieval.py`의 `CharacterNgramIndex`가 재사용 후보다. 다만 외부 모듈의 `name_view` 정규화·인덱스 행 순서·IDF 적합 범위를 현재 AR-06과 맞춰야 하며 바로 import만 하는 패치는 충분하지 않다. 이름 후보의 모든 동명 ID를 보존한다.

검색 합집합의 가변 후보 포함률, 현재 한글 lattice 재채점 Top-15 진입률, 선택한 고정 K의 최종 후보 포함률, 최종 ID Fix/Break를 구분한다. 새 후보가 존재해도 재채점 전에 밀려나면 최종 성능은 달라지지 않을 수 있다. 실제 test의 후보 누락 건수와 발생 원인은 미측정이다.

## 3. train 자산과 톤수 점수

`fit_matching_model(train_df, catalog_df, ...)`는 전체 train으로 최종 학습하며(`run_ar06.py:2201`부터), 단독 `script.py`는 추론 때 저장된 JSON을 읽는다. 추론 시 train.csv를 다시 읽는 구현은 필요하지 않다.

두 현재 모델 JSON의 SHA-256은 같다: `5a70a74ec75e33d03ba1e676559d95183f7a091b3a38926c30f4e7792346e650`. 호출부호 5,851개, 이름 5,857개, 학습 단어 466개, 학습 음절 271개와 선종·국적 통계가 들어 있다. callsign_lookup은 현재 train의 키·정답과 모두 일치한다. 학습 단어·음절 수만으로 모든 자산의 재학습 일치나 무누수를 증명한 것은 아니다.

현재 한글 톤수 점수(`script.py:1916`부터):

| 조건 | 기존 가산 |
|---|---:|
| 절대 차이 ≤1 | +3.6 |
| 카탈로그 GT 기준 상대 오차 ≤0.5% | +3.1 |
| 상대 오차 ≤2% | +2.5 |

GT와 IGT 중 더 작은 차이를 사용한다. 따라서 제안한 1.5% 이내 후보는 이미 위 조건 중 하나에서 양의 점수를 받는다. 국적·선종은 별도 메타 점수에 들어간다. 새 가산은 **중복된 증거를 얼마나 더 강조할지**의 문제이며 기능 누락을 고치는 작업이 아니다.

가산 실험은 `best_sim` 대신 실제 `sim_alpha`·`sim_phon` 중 무엇을 기준으로 할지, 적용 언어·유사도 범위·결측 처리·선종/국적 호환 정의·가산 크기를 먼저 고정한다. 카탈로그 GT 기준 상대 오차 ≤1.5%, 이름 증거가 일정 수준 이상이며 숫자 충돌이 없는 후보에 한정한 작은 상호작용 항을 후보로 둘 수 있다. 기존 국적/선종 점수까지 함께 바꾸지 않고 단일 요인으로 비교한다. 가까운 톤수 자매선의 Break와 이름이 다른데 제원만 맞는 후보의 역전을 검사한다.

## 구현·검증 순서

1. 안전 조회 자산 스키마와 설정 전달: G5는 unseen 퇴보 검사, 고정 행 분할은 seen 효과 확인. 매번 fit fold에서만 조회표를 만든다.
2. 기존 점수·lookup off를 고정하고 전역 n-gram 하나만 추가해 후보 포함·최종 Fix/Break·평균/P95 후보 수·단계별 시간을 비교한다. 전역 골격과 J/S/Z 통합은 별도 요인이다.
3. 동일 후보를 고정한 뒤 톤수·메타 상호작용 가산만 비교한다. 3개 변경을 한꺼번에 적용한 점수로 원인을 추정하지 않는다.
4. 작은 공개 보류 진단 뒤 공통 G5 전체를 퇴보 검사하고, 기존 공개 train 전체를 과거부터 미사용한 독립 최종 테스트라고 부르지 않는다. 현재 Windows에는 지정 `.venv-server`가 없어 모델 실행 검증은 미실시다. 과거 Linux 환경 JSON은 이 PC의 설치 확인이 아니다.

### 생성 경로 주의

`run_ar06.py`의 `CORE_ENGINE_CODE`로 학습·평가와 제출 스크립트를 만든다. 단독 `AR-06/script.py`에만 패치하면 재생성 때 반영되지 않는다. 현재 단독 파일과 `train_AR-06/script.py`의 차이는 `top_candidates` 반환 지원으로 확인했으며 실행 동등성은 이번에 검사하지 않았다. 코드 변경 시 생성 엔진과 실제 사용 패키지를 함께 검증해야 한다.

현재 `run_ar06.py`는 OOF 뒤 ZIP 생성과 제출 검사까지 자동 실행한다. 후속 성능 실험 전에 명시적 ZIP 옵션과 평가/학습 경로를 분리해야 한다. 이번에는 이 실행기를 실행하지 않았고 기존 코드·모델·ZIP을 변경하지 않았다. 이는 이번 요청의 분석 범위이며, 구현·성능 검증이 완료됐다는 뜻이 아니다.
