# AR-06 / AS-05 후보 검색 보강 계획

상태: **planned**. 코드 검토와 제안만 완료했으며 구현·성능 실측·ZIP 갱신은 하지 않았다. 기록 시각: 2026-10-25T10:51:42+09:00.

## 우선 적용할 안

기존 후보를 유지하면서 **톤수와 독립적인 전역 문자 2~4gram 검색**을 추가한다. 기존 `model/ngram_retrieval.py`의 `CharacterNgramIndex`를 재사용하되 AS-05의 정규화·import 경로에 맞게 연결하고 동점은 vessel_id로 처리한다. IDF와 어휘는 공식 카탈로그에서만 만든다.

초기 예산은 기존 구현을 참고해 비한글 24개, 한글 60개 이름 후보로 시작한다. 최적값이 아닌 실험 시작점이다. 같은 이름의 모든 선박 ID를 보존하며 이름 후보 수와 ID 수를 구분한다. 한글/비한글을 각각 비교해 득실을 분리한다.

## 현재 제출 코드에서 확인한 보강 지점

1. 이름·자음·발음 인덱스는 앞부분에 의존하는 경로가 많다. 비한글에는 이미 접미사와 톤수창 내부 OSA 검색이 있으나, 톤수와 독립된 전역 근사 검색은 연결돼 있지 않다.
2. 일부 확장 조건은 후보 200개 미만 또는 빈 집합이다. 관련 없는 후보가 많으면 탐색을 충분히 했다고 간주될 수 있다. 이름 매칭 품질·이름/제원 후보의 충돌·결측으로 확장을 결정하는 별도 비교를 제안한다.
3. 한글 전체 이름 변형은 각 단어의 같은 순위 해석을 이어 붙인다. 서로 다른 순위 조합을 포함하는 유계 탐색으로 6~8개 질의를 만드는 방안을 제안한다. 대형 생성 모델 호출이 아닌 문자열 조합이다.
4. 이미 계산하는 발음 문자열에도 전역 n-gram 인덱스를 추가할 수 있다. 철자와 발음이 다른 음역 사례를 보완하는 별도 경로로 비교한다.
5. 숫자 인덱스는 해당 번호 후보가 500개를 넘으면 건너뛴다. 숫자+이름 조각을 함께 평가하는 경로로 대체 가능하다. 로마 숫자·서수 변형은 원본도 보존하고 후보 해석으로만 사용한다.
6. 새 후보가 원래 점수 때문에 Top-35 밖으로 밀리면 LM이 볼 수 없다. 합집합 단계와 최종 Top-35의 정답 위치를 따로 기록한다. 새 경로 보호 슬롯은 기존 후보를 밀어낼 수 있으므로 같은 K에서 별도 비교한다.
7. 완전 빈 집합이면 현재는 카탈로그 0번 행을 사용한다. 이름이 있으면 전역 검색, 이름 정보가 없으면 고정 제원 검색으로 대체하고 ID로 동점을 처리하는 방안을 제안한다.

## 분리해서 비교할 순서

- A: 기존 검색 vs 기존 검색+전역 문자 n-gram. 점수 함수·메타 보정·LM·결합 가중치를 고정한다. 후보 증가 효과와 최종 Fix/Break를 분리한다.
- B: 한글 혼합 해석 및 발음 전역 검색을 별도 비교한다.
- C: 후보 개수 중심 확장을 품질·결측·충돌 기반 확장으로 바꿔 비교한다. 정답 여부나 테스트 전체 남은 시간으로 호출을 결정하지 않는다.
- D: 같은 고정 K에서 후보 압축 전략을 비교한다. K가 달라지면 비용과 후보 포함률을 별도 보고한다.

보류 50~100행의 초기 진단에는 첫 글자·어순·약어·숫자·톤수 결측/큰 오차를 다루되 원래 맞히던 대조군도 포함한다. 합성 변형은 실제 테스트 분포와 구분한다. 현재 Fold0 Top-35는 전 행 정답을 포함하므로 깨끗한 해당 집합만으로 검색 보강 효과를 입증하기 어렵다.

측정: 합집합의 가변 후보 포함률, 압축 후 Recall@35(또는 동일 고정 K), 새 경로만 복구한 수, 최종 ID Fix/Break, 평균/P95 후보 ID 수, 인덱스·검색·점수 계산 시간과 LM 호출 수. 표본 정확도를 전체 서버 성적으로 외삽하지 않는다.

과거 `docs/RETRIEVAL_COMBINATIONS.md`는 모듈 재사용 근거이며 다른 모델·분할 실험이다. 당시 성능을 AS-05 개선 수치로 사용하지 않는다. 첫 단계는 LM 호출 방식은 유지하고 가벼운 검색 경로만 추가한다. 30분 충족 여부는 실제 검색 시간 표본으로 확인해야 한다.
